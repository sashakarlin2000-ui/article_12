# Глобальный план работы над исследованием

## Прогнозирование фондового рынка с использованием режимов, исторических аналогов и ансамбля LLM

Проект посвящён проверке того, улучшают ли:

- определение рыночного режима;
- поиск похожих исторических ситуаций;
- использование нескольких LLM;
- ансамблирование прогнозов;
- режимно-зависимые веса;

качество прогноза направления движения фондового рынка и торговые результаты по сравнению с простыми и классическими моделями.

Все роли работают над одной общей исследовательской системой. Главный принцип проекта: **до финального теста нельзя использовать будущую информацию и нельзя подбирать метод по результатам финального тестового периода**.

---

# Общая архитектура проекта

```text
Исторические данные
        ↓
Очистка и расчёт признаков
        ↓
Определение рыночного режима
        ↓
Поиск исторических аналогов
        ↓
Прогнозы нескольких LLM
        ↓
Ансамбль прогнозов
        ↓
UP / DOWN / HOLD
        ↓
Backtest
        ↓
Классификационные и торговые метрики
        ↓
Статистический анализ
        ↓
Научная статья
```

## Общие правила для всех ролей

1. Все данные обрабатываются хронологически.
2. Для прогноза на дату `T` разрешены только данные, доступные до момента формирования прогноза.
3. Будущие даты нельзя использовать при расчёте признаков, режимов, retrieval и весов ансамбля.
4. Финальный тестовый период нельзя использовать для настройки параметров.
5. Все функции должны иметь понятный входной и выходной формат.
6. Каждый модуль должен иметь минимальные тесты и пример запуска.
7. Ошибки нельзя скрывать за пустыми или успешными результатами.
8. Каждый результат должен быть связан с конкретной версией данных, кода и конфигурации.

# Роль №2 — Режимы рынка

## Задача проекта для роли

Разделить рынок на несколько состояний и добавить к каждой строке колонку `market_regime`.

## Начальные режимы

- `Bull`;
- `Bear`;
- `Sideways`;
- `High Volatility`.

Важно: эти названия являются интерпретацией, а не исходным знанием алгоритма.

## Что сделать

### 1. Подготовить признаки режима

Использовать:

- `return_5d`;
- `volatility_20d`;

Дополнительно можно использовать:

- `distance_from_MA20`;
- `distance_from_MA200`;
- `return_1d`;
- `volatility_5d`;
- drawdown;
- объёмные признаки.

### 2. Реализовать кластеризацию

Начать с:

```python
KMeans(n_clusters=4)
```

Признаки нормализовать через `StandardScaler`.

Дополнительно попробовать:

- `GaussianMixture`;
- rule-based классификацию;
- HMM только при корректном использовании фильтрованных состояний.

### 3. Интерпретировать кластеры

Для каждого кластера рассчитать:

- средний `return_5d`;
- среднюю `volatility_20d`;
- среднее расстояние до MA;
- количество наблюдений;
- среднюю длительность режима;
- переходы между режимами.

Пример интерпретации:

```text
positive return + low volatility  → Bull
negative return + high volatility → Bear
small return + low volatility     → Sideways
high volatility независимо от знака → High Volatility
```

Нельзя автоматически переименовывать кластеры без таблицы характеристик.

### 4. Point-in-time проверка

Если режим используется в финальном прогнозе, detector должен быть обучен только на доступной истории. Нельзя обучать кластеризацию на всём датасете перед тестированием.

## Что должно получиться

- `regime_detector.py`;
- `market_data_with_regime.csv`;
- таблица характеристик кластеров;
- график режимов по времени;
- описание выбранного алгоритма;
- тест на отсутствие использования будущих данных.

### Передача следующей роли

Передать роли №3, №4 и №5:

- параметры detector;
- таблицу характеристик режимов;

# Роль №3 — Поиск исторических аналогов

## Задача проекта для роли

Написать функцию, которая для текущего дня ищет похожие ситуации в прошлом.

Пример интерфейса:

```python
find_similar_days(current_day, top_k=3)
```

## Вектор текущего состояния

Использовать:

- `return_5d`;
- `volatility_5d`;
- `volatility_20d`;
- `RSI`;
- `distance_from_MA20`;
- `distance_from_MA200`.

При необходимости можно добавить признаки режима, но режим не должен заменять исходные признаки.

## Что сделать

### 1. Нормализация

Признаки нормализовать через параметры, рассчитанные только на допустимой прошлой истории.

### 2. Метрика сходства

Начать с:

```python
Cosine Similarity
```

Использовать инструменты `scikit-learn`.

FAISS пока не является обязательным.

### 3. Ограничение по времени

Для даты `T` разрешены только кандидаты:

```text
date < T
```

Запрещены:

- текущая дата;
- будущие даты;
- окна, пересекающие прогнозный период;
- исторические записи, содержащие будущую информацию.

### 4. Обычный retrieval

```text
текущий день
      ↓
поиск по всей допустимой истории
      ↓
Top-k аналогов
```

### 5. Regime-aware retrieval

```text
текущий день
      ↓
текущий regime = BEAR
      ↓
оставить только BEAR
      ↓
найти Top-k аналогов
```

### 6. Формат результата

Пример:

```text
Current date: 2024-03-10
Current regime: BEAR

Similar days:
2020-03-12 | similarity 0.94 | next return -2.1%
2022-06-13 | similarity 0.92 | next return -1.8%
2018-12-20 | similarity 0.90 | next return +0.4%
```

Если будущая доходность используется для анализа, она должна быть отделена от информации, передаваемой прогнозирующей модели.

## Что должно получиться

- `retrieval.py`;
- обычный retrieval;
- regime-aware retrieval;
- несколько примеров результатов;
- `retrieval_records.csv`;
- тесты на запрет будущих дат;
- описание fallback при малом количестве аналогов.

### Передача следующей роли

Передать ролям №4 и №5:

- API retrieval;
- формат аналогов;
- значения similarity;
- текущий режим;
- правила исключения будущих данных.

Пока LLM не подключены, использовать тестовые данные.

Пример:

```text
GPT       → UP   confidence 0.80
Gemini    → UP   confidence 0.70
DeepSeek  → DOWN confidence 0.60
Llama     → UP   confidence 0.75
```

## Что сделать

### 1. Majority Voting

```text
UP
UP
DOWN
UP
↓
UP
```

### 2. Confidence Weighted Voting

Пример входа:

```python
[
    {"model": "gpt", "prediction": "UP", "confidence": 0.80},
    {"model": "gemini", "prediction": "UP", "confidence": 0.70},
    {"model": "deepseek", "prediction": "DOWN", "confidence": 0.60},
    {"model": "llama", "prediction": "UP", "confidence": 0.75}
]
```

Основная функция:

```python
make_ensemble_decision(responses)
```

Пример выхода:

```python
{
    "prediction": "UP",
    "score": 0.41,
    "method": "confidence_weighted_voting"
}
```

### 3. Режимно-зависимые веса

После появления validation-прогнозов добавить:

## Этап 5. Проверка качества исследования

### Проверить data leakage

- режимы не обучаются на test;
- retrieval не видит будущие даты;
- нормализация не использует test;
- веса ensemble выбираются на validation;
- HMM не использует сглаженные состояния;
- target не попадает во входной prompt;
- исторические аналоги не содержат будущий результат в контексте модели.

### Проверить воспроизводимость

- повторный запуск даёт одинаковую структуру;
- seeds сохранены;
- prompts сохранены;
- версии моделей сохранены;
- API-ошибки записаны;
- результаты имеют `run_id`;
- случайные изменения не попадают в финальный отчёт.

# Контрольные точки проекта

## Gate 1 — данные

Переход дальше запрещён, если:

- есть неизвестные пропуски;
- есть дубликаты;
- смешаны тикеры;
- неверно рассчитан target;
- не зафиксирован источник данных.

## Gate 2 — режимы и retrieval

Переход дальше запрещён, если:

- режим использует будущее;
- retrieval возвращает будущие даты;
- нормализация обучена на test;
- нельзя объяснить смысл кластеров.

## Gate 3 — LLM и ensemble

Переход дальше запрещён, если:

- не сохраняются prompts;
- не сохраняются raw responses;
- невалидные ответы превращаются в случайный сигнал;
- модели получают неодинаковую информацию;
- веса выбраны по финальному тесту.

## Gate 4 — backtest

Переход дальше запрещён, если:

- не определено время исполнения;
- не учтены комиссии;
- equity curve не совпадает с таблицей сделок;
- отсутствует сравнение с Buy & Hold.

## Gate 5 — статья

Статья не считается готовой, если:

- отсутствуют фактические результаты;
- числа в статье не совпадают с таблицами;
- нет статистической проверки;
- отсутствует анализ ограничений;
- скрыты отрицательные результаты;
- не описана воспроизводимость.

# Ближайший порядок действий

1. Тимлид фиксирует протокол и интерфейсы модулей.
2. Роль №1 завершает и проверяет датасет.
3. Роль №2 добавляет рыночные режимы.
4. Роль №3 реализует обычный и regime-aware retrieval.
5. Роль №6 параллельно завершает baseline backtest на тестовых predictions.
6. Роль №5 завершает mock-ensemble.
7. Роль №4 подключает LLM и сохраняет единые JSON-ответы.
8. Роли №4 и №5 проводят E2–E6.
9. Роль №6 считает все классификационные и торговые метрики.
10. Тимлид проводит leakage audit и замораживает финальный прогон.
11. Команда выполняет статистический анализ и robustness checks.
12. Тимлид обновляет статью результатами.
13. Команда проводит внутреннее рецензирование.
14. Тимлид адаптирует статью под выбранный журнал.
